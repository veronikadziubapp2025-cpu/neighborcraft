# Протокол тестування форми NeighborCraft

Фактичний результат і статус залишені порожніми для ручного проходження. Протокол описує очікування за поточним кодом і `validation-rules.md`; відкриті питання винесені окремо.

## Знайдені розбіжності

Аналіз виконаний читанням `assets/js/validation.js`, `index.html` і `validation-rules.md`; код для цього аналізу не запускався.

| Проблема | Причина | Рішення |
|---|---|---|
| Конкретне повідомлення для перевищення максимальних меж не відповідає загальному тексту помилки, очікуваному деякими edge-case критеріями. | `validateName()` перевіряє 2–50, `validateMessage()` — 10–1000, `validateEmail()` — максимум 254, але кожна функція використовує один зафіксований текст помилки для всіх невалідних значень. Це збігається з поточними правилами у `validation-rules.md`, але не з очікуванням «конкретний текст про ліміт». | Код не змінювався: змінити лише після рішення, чи додавати окремі тексти та оновлювати правила/тести разом. |
| Рахування довжини для емодзі використовує UTF-16 code units. | Функції використовують `String.length`; один емодзі поза BMP рахується як 2. | Валідацію не змінював: поточні правила визначають довжину, але не одиницю підрахунку. Потрібне рішення, чи перейти до `[...value].length`. |
| Дозволеність цифр та інших символів у імені не визначена окремою забороною. | `validateName()` перевіряє тільки обрізану довжину 2–50; `12345` проходить. Це узгоджено з правилом «будь-які символи» у `validation-rules.md`. | Код не змінювався; підтвердити, чи цифри мають прийматися. |
| Момент перевірки після автозаповнення залежить від браузерних подій. | Текстові поля слухають `input` лише для touched-полів і `blur`; submit завжди перевіряє всі значення. Браузери можуть по-різному повідомляти про autofill. | Зміна не потрібна для коректності submit; перевірити autofill на цільових браузерах і вирішити, чи потрібен додатковий механізм. |
| Поведінка кнопки Back не визначена. | Форма не зберігає стан в історії; правила не задають його відновлення після навігації. | Код не змінювався. Зафіксувати бажане очікування для цільових браузерів. |
| Опис стану Normal у правилах не відповідає поточній вимозі доступності. | `validation-rules.md` каже, що в Normal немає `aria-invalid`, тоді як актуальна розмітка й `clearError()` задають `aria-invalid="false"` за вимогою етапу Accessibility. | Код не змінювався: правило валідації не зачіпалося. Синхронізувати опис стану після підтвердження, що актуальним лишається явний `false`. |

Інших розбіжностей у перевірених критеріях коду не виявлено:

- У DOM не додаються введені значення; динамічні рядки записуються через `textContent`, `innerHTML` не використовується.
- Слухачі встановлюються один раз усередині одного `DOMContentLoaded`; `isSubmitting` захищає 600-мс імітацію від повторного submit.
- Ім'я перевіряється після `trim` у межах 2–50; повідомлення — 10–1000; email — regex і довжина до 254; телефон — суворий `REGEX_PHONE`; згода має бути відмічена.
- Рядки лише з пробілів відхиляються після `trim`; зовнішні пробіли email обрізаються лише для перевірки.
- Успішний submit викликає `form.reset()` і `clearError()` для кожного поля: рамки повертаються до Normal, помилки й іконки ховаються, `data-valid` видаляється, `aria-invalid` повертається до `false`, підказка телефону та її `aria-describedby` очищуються.
- `validateForm()` перевіряє всі поля до відкриття модалки та фокусує перше невалідне.
- Підказка телефону не змінює значення автоматично; заміна відбувається лише після явної дії користувача.

## Висновок

Протокол містить **53 сценарії**: 17 основних і негативних та 36 edge cases. За аналізом коду реальних помилок реалізації, що суперечать поточним правилам, не виявлено; виправлень у `validation.js` або `index.html` не знадобилося. Виявлено розбіжність між описом Normal у `validation-rules.md` і вимогою явного `aria-invalid="false"`. Залишилися відкритими: окремі тексти для перевищення максимумів, підрахунок емодзі як code points, допустимість цифр у імені, миттєва реакція на autofill у різних браузерах, очікування для Back і синхронізація опису Normal. Колонки фактичного результату й статусу залишені порожніми для ручного тестування.
